# 面试重点

答法：先给判断，再给一个结构，最后用一个例子收住。不背 API 字段。标星沿用原书难度感觉：★ 概念，★★ 要能设计，★★★ 要能取舍。

## 概念

### ★★ 模型、上下文、工具只能加一项，你加哪个？

默认加上下文。模型只能根据看见的信息行动；工具定义和结果也是上下文的一部分。任务是“看得到但做不到”时才加工具，是“信息齐了仍不会做”时才换模型或后训练。

条件会变：高风险动作缺一个受控接口，加专用工具；风格和感知怎么写提示都稳不下来，改参数；业务规则每周变，写 Skill 而不是微调。

### ★★ 为什么模型越强，Harness 反而更重要？

模型吃掉的是适配层：逐步思考的套话、JSON 修补、文生图提示词改写。吃不掉的是业务约束、权限、验证和此刻还做不稳的前沿。自主空间变大，出错的影响面也变大。Harness 随模型一层层外移，不会一次性消失。

### ★★ 工作流还是自主 Agent？

路径必须固定、搞错顺序会出资金或合规问题，用工作流。步骤数事先不知道、要靠环境反馈改计划，用自主 Agent，并写明停止条件。订票可以身份和支付走工作流，改签和异常走自主。能用一次模型调用解决的，两者都不要上。

### ★ 提议者—审核者为什么不能是同一个上下文？

同一上下文既生产盲区，也很难发现自己被注入。审核者应看到测试输出、截图或结构化参数，看不到对方的自我辩解。代码审查看 diff 和测试，不看作者的思考过程。

## 上下文与记忆

### ★★ 怎样既不撑破窗口，又不打掉 KV Cache？

系统提示和工具定义永不改写。历史只追加。大工具结果落盘，上下文里留冻结的摘要，替换字符串以后不要再变。接近阈值再批量压缩旧的工具结果，而不是每轮滑动删除。探索性的大段阅读交给子 Agent，主上下文只收结论。动态时间戳放在最新一条消息，不写进系统提示。

### ★★ 上下文腐化和窗口溢出有何不同？

溢出是装不下，任务中断。腐化是装得下但找不到：注意力被无关 token 稀释，决策变差，表面仍在正常运行。开头和结尾更受关注，中间容易丢。所以要主动写成可检索的结论，而不是把原始日志堆着。

### ★★ 用户说了两个住址，记忆怎么处理？

不要静默覆盖。短期可以两条都留，带时间和来源。检索时按时间排序，必要时向用户确认哪条仍有效。写入阶段就删除旧事实，一次抽错会不可逆。Mem0 从写入时 UPDATE/DELETE，改成只追加、检索时消歧，就是这个取舍。关键身份字段可以用结构化卡片；冲突检测也可以写成代码。

### ★★ 传统 RAG 和智能体化 RAG 怎么选？

问题单跳、查询已经明确，一次检索更快，也够用。问题要拆开、第一次关键词会偏，让 Agent 把检索当工具，看结果再改查询。代价是延迟和 token。两种都要做指令和数据分离，并且检索按权限过滤。

## 工具与安全

### ★★ 一项能力做成专用工具还是 Skill？

先问四个问题：要不要细粒度审计，参数是不是嵌套且易错，改得频不频繁，模型够不够强。安全和高风险用专用工具。流程经常变、参数简单，用 Skill 加通用执行器。这和“一次展示多少条”无关。一百个专用工具也可以只暴露索引，按需加载。

### ★★ 工具调用老选错，你先查什么？

先查描述：何时用、何时不用、边界、参数例子、返回结构。多数错误是模型不知道这个工具不能做什么。换模型的收益通常低于改描述。同时检查参数层有没有静默改写。

### ★★★ 怎样防提示注入？

上下文层做来源标注和指令/数据分离，只能降概率。执行层用独立于该上下文的权限、沙盒和人工确认。数据层用数据库约束兜底，即使生成的代码漏了判断也写不进去。三要素不要同时无限制打开：私有数据、不可信内容、对外通信。长期记忆的写入按不可信内容审查。

## 评估与训练

### ★★ p=0.6，你汇报 Pass@5 还是 Pass^5？

看失败代价。Pass@5 约 99%，表示多试几次几乎能碰上一次，适合挖洞和创意草稿。Pass^5 约 7.8%，表示连续五次都对很难，适合退款和部署。有副作用就不能在真实环境里重试到成功。报告必须写清 k 是同一任务的独立采样，还是生产上连续 k 单。

### ★★ LLM 评判 LLM，盲区在哪？

评判模型会偏爱某种文风，也可能和被评模型共享盲区。量表要逐项、要引用轨迹位置、证据不足就拒评。用人类抽检和确定性检查（测试、数据库）锚定结果层和过程层。主观维度不要假装能变成一个客观总分。

### ★★ 什么时候 SFT，什么时候 RL？

pass@k 接近 0，说明成功轨迹几乎抽不出来，先 Mid-training 补知识或能力。输出格式不稳，奖励无法计算，先 SFT。已经偶尔能做成，再用 RL 把这条策略的概率抬高。SFT 样本效率高，容易学表面模式；RL 贵，奖励一偏就会奖励黑客。数据和环境先于算法。

### ★★★ 多轮任务的功劳怎么分？

最终成败太稀疏，分不清是第 3 轮还是第 7 轮的决策。能用规则判定的中间状态就给过程信号，例如测试从失败变通过、违规动作即时惩罚。结果仍然要查，避免“过程好看但结果造假”。路径约束可以惩罚投机步骤，即使终点碰巧正确。蒸馏则把一次成功轨迹变成更密的 token 级监督，用来提高样本效率。

## 系统设计

### ★★ 客服 Agent 的“虚假承诺”改哪里？

先看证据。模型不知道政策，补知识库。知道政策但边界说不清，改 Skill，并写例外。承诺必须和真实退款状态一致，用代码对照工具日志，对不上就不许发送。语气问题才考虑后训练。三层可以同时在，但发布时用边界集证明虚假承诺下降，用保留集证明正常退款没有被误伤。

### ★★ 什么时候上多 Agent？

先问协作有没有新信息。执行测试、看截图、用外部来源核验、在开放空间里分工搜索，有。两个副本互相读对方的思考，通常没有。然后再看 token 倍数是否划算。隔离上下文，用移交包通信。同质审核不算独立证据。给循环加预算和取消，避免子 Agent 数量失控。

### ★★★ 长任务如何避免上下文耗尽和过早宣布完成？

稳定前缀不动。计划、进度和失败路径写到文档，不全部留在聊天里。大探索用子 Agent。压缩保留决策、约束、失败原因和来源。完成由验证器判定，不由模型的一句“done”判定。初始化会话负责搭环境和任务列表，后续会话增量推进并留下交接物。连续失败要熔断。

### ★★ 缓存友好和“每轮更新用户余额”矛盾吗？

不把余额写进系统提示。需要时用工具读，或作为最新消息追加。若状态栏每轮都改写前缀中间，缓存和已绑定思考会失效。状态栏应追加新快照，或由代码在不改历史的前提下只更新末尾。

### ★★★ 模型会不会让 Agent 工程师失业？

模型会内化今天的脚手架，所以只维护适配层的优势是临时的。留下来的工作是：定义观察和动作、把业务约束放在可验证的层、建立评估和回滚、决定一次变更该写进知识、Skill、代码还是参数。这些判断不随某一代 API 过期。

## 临考前十句

1. Agent = LLM + 上下文 + 工具；环境在边界外。
2. Harness = 上下文 + 工具 + 约束 + 验证 + 纠正。
3. 上下文 = 静态前缀 + 只追加的轨迹。
4. 前缀不改，动态信息放末尾，消息走标准 API。
5. 验证看结构化事实，不看模型自述。
6. 披露和工具形态是两个决定。
7. Pass@k 看上限，Pass^k 看可靠性。
8. 底座用 Mid-training，协议用 SFT，策略用 RL；pass@k 接近 0 不要硬上 RL。
9. 进化四载体：知识、指令、程序、参数；在线记录，离线发布。
10. 多 Agent 的价值等于它带来的新信息，减去多出来的 token 和失败模式。
